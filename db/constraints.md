# Обоснование ограничений

## Как заполнять

- **CHECK, UNIQUE, FK** — обосновывать обязательно. Ссылка на `BR-N.M` + краткое «почему».
- **NOT NULL** — обосновывать **только** когда бизнес явно требует. Очевидные случаи (PK, FK на NOT NULL поле, поля из BR с явным «обязательно») — не дублировать.
- **NULL** (где разрешено) — обосновывать, потому что это осознанное решение, а не забывчивость.
- **DEFAULT, GENERATED** — кратко, если не очевидно.

**Правило:** если не можешь указать `BR-N.M` — либо ограничение лишнее, либо пропущено бизнес-правило. Разберись, прежде чем оставлять.

**Формат обоснования:** «<что ограничиваем> — потому что <BR-N.M> требует <что>».

Пример хорошего обоснования:

> `CHECK (rating BETWEEN 0 AND 5)` на `restaurant.rating` — потому что BR-4.2 задаёт диапазон рейтинга.

> `UNIQUE (address_id)` на `restaurant` — потому что BR-3.3 запрещает двум ресторанам делить один адрес.

> `FK (restaurant_id) → restaurant(restaurant_id)` на `product` — потому что BR-5.1 требует, чтобы блюдо принадлежало ресторану.

Пример плохого обоснования (не принимается):

> `NOT NULL` на `name` — потому что имя должно быть.

> `CHECK` на `price` — потому что цена не может быть отрицательной.

(Второе — обоснование «здравым смыслом», а не ссылкой на BR. Не принимается.)

## Ловушки

Здесь — не готовые решения, а **фиксация того, как ты решил** каждую ловушку. Преподаватель читает, чтобы понять ход мысли.

### Ловушка 1: `payment` — неполная сущность

**Какие атрибуты добавил в `payment` и почему** (BR-8.2):

```
в соответствии с BR-8.2 добавлены атрибуты:
payment_type payment_type - тип платежа. 
amount numeric(10, 2) - сумма оплаты с точностью до копеек
transaction_id varchar(100) - BR-8.3. Идентификатор финансовой транзакции — внешний, приходит от платёжного провайдера. Неизвестно в каком виде он будет приходить, поэтому символьный тип данных
payment_timestamp timestamp - дата и время транзакции
status payment_status - статус
```

**Где хранится тип оплаты — `payment` или `order`** (BR-8.6):

```
BR-8.6 прямо говорит: Тип оплаты относится к попытке оплаты, а не к заказу. У заказа может быть несколько попыток с разными типами (например, клиент начал платить картой, не получилось, оплатил наличными при получении). 
В связи с этим тип конкретной попытке оплыты храним в payment
```

**Как обеспечено, что адрес доставки принадлежит клиенту:**

Составной FK на таблицу client_address обеспечивает принадлежность адреса клиенту
constraint fk_order_client_address foreign key (client_id, address_id) references client_address (client_id, address_id);

### Ловушка 3: `order_structure` — один ресторан в заказе (BR-7.3)

**Как обеспечено, что все блюда из `order.restaurant_id`:**

```
наличие поля restaurant_id в order_structure было бы избыточно. Реализовал триггер trg_check_order_product_restaurant, работающий на добавление и обновление записей. Сравнивает order.restaurant_id и product.restaurant_id
```

### Ловушка 4: `review` — полиморфизм (BR-9.1)

**Как реализована валидность `review.entity_id`:**

Сюда — **только** те `NOT NULL`, которые нельзя объяснить очевидностью.

**Не дублируй:**
- PK (всегда NOT NULL по определению);
- FK на NOT NULL поле (очевидно, если родитель NOT NULL);
- поля из BR с явным «обязательно» — только если хочешь подчеркнуть, что это не случайность.

## Нормализация (3НФ)

Короткое обоснование, что все таблицы в 3НФ:

```
Все атрибуты атомарны и хранятся в отдельных столбцах(1НФ). Все неключевые атрибуты зависят от полного PK (2НФ). Нет транзитивных зависимостей (3НФ).

address - учитывая, что работаем в рамках одного города, нет смысла создавать таблицу улиц и нарушения 3НФ тут нет. Чтобы не было ошибок при ручном вводе улиц, я бы отвел для улиц отдельную таблицу, но, похоже, это сломает тест C.5 `-- и аналогично для других varchar-полей с NOT NULL`, т.к. в erd строковое поле улицы задано именно в таблице address
restaurant.company_details - судя по BR-4.5 должно быть общим полем, но по логике я бы разделил на отдельные ИНН, ОГРН и р/с

Особые случаи:
- order.commission = 10% от order_amount — вычисляемое через `GENERATED ALWAYS AS`. Обоснование приведено в выше.
- order.total_amount = order_amount + commission — вычисляемое через `GENERATED ALWAYS AS`. Обоснование приведено в выше.
- product.rating и restaurant.rating — агрегаты, поддерживаются триггером rating_change. Это осознанная денормализация для скорости чтения, иначе для отображения рейтинга приходилось бы каждый раз рассчитывать его по огромному количеству отзывов. Требования BR-9.6, BR-9.7.
- review.entity_id + entity_type — полиморфизм. Не нарушает 3НФ, потому что запись все еще описывает атрибуты отзыва, а не сущности к которой привязана. 
```
