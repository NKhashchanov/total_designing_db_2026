# Бэклог FoodExpress

## Как читать

Каждый тикет — отдельная задача. Идентификаторы `FOOD-NNN` стабильны: ссылайся на них в `constraints.md` и `tests.md`.

`AC` = acceptance criteria. Тикет считается закрытым, когда все галочки проставлены.

Ссылки `BR-N.M` указывают на бизнес-правило в `docs/company-rules.md`.

## FOOD-105. Триггер пересчёта рейтинга

**Контекст.** При добавлении/изменении/удалении отзыва нужно пересчитать агрегированный рейтинг блюда или ресторана. У заказа агрегата нет (BR-9.6).

**AC:**

- [ ] Триггерная функция `rating_change()` возвращает `TRIGGER`.
- [ ] Триггер срабатывает на `INSERT`, `UPDATE` и `DELETE` в таблице `review`.
- [ ] Если `entity_type = 'блюдо'`: пересчитывает `product.rating = AVG(review.rating)` по всем отзывам на это блюдо.
- [ ] Если `entity_type = 'ресторан'`: пересчитывает `restaurant.rating = AVG(review.rating)` по всем отзывам на этот ресторан.
- [ ] Если `entity_type = 'заказ'`: ничего не пересчитывает (у заказа агрегата нет).
- [ ] При удалении отзыва рейтинг пересчитывается.
- [ ] При обновлении отзыва (`entity_type` или `entity_id` или `rating`) рейтинги пересчитываются для затронутых сущностей.
- [ ] Если отзывов на сущность нет — `rating = NULL`.
- [ ] Триггер не вызывает бесконечной рекурсии.

**Проверка:** вставка 3 отзывов на одно блюдо с рейтингами 3, 4, 5 → `product.rating = 4`. Удаление одного → `product.rating = 4.5`. Удаление всех → `product.rating IS NULL`.

**AC:**

- [ ] Колонки строго с этими именами (контракт бэкенда):
  - `restaurant_name`
  - `best_product_name`
  - `total_amount`
  - `avg_amount`
  - `best_user`
- [ ] `restaurant_name` — название ресторана.
- [ ] `best_product_name` — самое покупаемое блюдо ресторана (по `SUM(quantity)` в `order_structure` для доставленных заказов). Если таких несколько — случайное.
- [ ] `total_amount` — сумма `order.total_amount` доставленных заказов ресторана.
- [ ] `avg_amount` — средняя `order.total_amount` доставленных заказов ресторана.
- [ ] `best_user` — ФИО клиента, который чаще всего покупает в ресторане (по количеству доставленных заказов). Если несколько — случайный. **Учти: ФИО в нашей схеме хранится только у курьеров, у клиента — логин (BR-2.6). Поэтому `best_user` = `client.login` — это осознанное решение бизнеса.**
- [ ] Учитываются только заказы со статусом `'доставлен'`.
- [ ] Один ресторан — одна строка в результате.
- [ ] Запрос оптимизирован по BR-11.8: без избыточных окон, без многократного сканирования одной таблицы.

**Проверка:** на сгенерированных данных функция возвращает по строке на каждый ресторан, `total_amount >= avg_amount`, `best_product_name` и `best_user` не `NULL` при наличии заказов.

## FOOD-107. Зарплата курьеров

**AC:**

- [ ] Процедура `courier_salary()` без параметров.
- [ ] Считает количество доставленных заказов каждого курьера за текущий месяц.
- [ ] Определяет новый коэффициент по BR-10.2:
  - 0–150 → 0.1
  - 151–250 → 0.2
  - 251–500 → 0.3
  - \> 500 → 0.5
- [ ] Считает зарплату за текущий месяц = `courier.coefficient (текущий) × SUM(order.commission) по доставленным заказам курьера в этом месяце`.
- [ ] Вносит запись в `courier_pay` (`year`, `month`, `courier_id`, `amount`, `coefficient_used`).
- [ ] Обновляет `courier.coefficient` новым значением (действует со следующего месяца).
- [ ] Уволенные курьеры получают зарплату за месяц, но `coefficient` у них не обновляется.
- [ ] Повторный вызов за тот же месяц обновляет существующую запись, не создаёт дубликат.
- [ ] Не падает, если у курьера нет доставок (зарплата 0, коэффициент 0.1).

**Проверка:** после `insert_test_data(10)` вызов `courier_salary()` создаёт/обновляет записи, `courier.coefficient` меняется у работающих курьеров, у уволенных — нет.

## FOOD-108. Отчёт «сколько денег»

**AC:**

- [ ] Представление `how_much_money`.
- [ ] Колонки строго с этими именами:
  - `year_month` (тип `text`, формат `YYYY-MM`)
  - `sum_no_commission` (`numeric`)
  - `sum_with_commission` (`numeric`)
  - `commission` (`numeric`)
  - `prev_commission` (`numeric`)
  - `commission_diff` (`numeric`)
  - `courier_pay` (`numeric`)
  - `net_profit` (`numeric`)
- [ ] `year_month` — все месяцы от первого месяца с доставленными заказами до последнего.
- [ ] `sum_no_commission` — сумма `order_amount` доставленных заказов за месяц.
- [ ] `sum_with_commission` — сумма `total_amount` доставленных заказов за месяц.
- [ ] `commission` = `sum_with_commission - sum_no_commission`.
- [ ] `prev_commission` — значение `commission` за предыдущий месяц. `NULL` для первого месяца.
- [ ] `commission_diff` = `commission - prev_commission`.
- [ ] `courier_pay` — сумма `courier_pay.amount` за месяц.
- [ ] `net_profit` = `commission - courier_pay`.
- [ ] Месяцы без заказов присутствуют в результате (BR-11.9) с нулевыми суммами.
- [ ] Рекурсивный CTE для генерации серии месяцев.

**Проверка:** на сгенерированных данных отчёт покрывает все месяцы от первого до последнего доставленного заказа; `net_profit` для месяцев без заказов равен 0.
